# Патч №1 — CSS/режимы (уже применён и закоммичен ранее)

## Короткий вариант (однострочный commit message)

```
Fix CSS/resources silently skipped in mode 1; add mode switch to menu; fix SiteEntry env_path crash
```

---

## Развёрнутый вариант

### Что было исправлено

Диагноз: архив шёл в режиме 1 «Спасение текста», который сознательно
не скачивает CSS/картинки/аватары/смайлики (приоритет этих задач выше
`priority_ceiling` режима 1) — это не баг и не регрессия, а непрозрачное
поведение: пользователь не видел, что часть контента осталась
несобранной.

### Изменения по файлам

**`storage/database.py`**
Новый метод `QueueManager.count_deferred_by_mode(priority_ceiling)` —
считает задачи, отложенные текущим режимом (priority выше потолка),
отдельно от тех, что в backoff или упали с ошибкой.

**`scanner/downloader.py`**
Новое поле `DownloadStats.resources_deferred_by_mode`, заполняется в
конце `Downloader.run()` через вызов нового метода очереди.

**`run_commands/run_archive.py`, `run_commands/run_forum2x2_archive.py`**
После прогона в режиме 1, если остались отложенные ресурсы — печатается
явное предупреждение с числом и советом переключиться на режим 2 (без
пересканирования текста).

**`main.py`**
- Новый пункт меню `M` — смена режима (1/2) с описанием, что входит в
  каждый; сохраняется в `config.json`.
- Текущий режим форума №1 теперь отображается в шапке главного меню.

**`utils/site_registry.py`**
Отдельный найденный баг: `SiteEntry` требовало поле `env_path`, которое
нигде не заполнялось — падало при загрузке `sites_forum2x2.json`.
Добавлено заполнение `env_path` в `get_or_create_site` и обратная
совместимость в `load_registry` для уже существующих записей без этого
поля.

**`tests/test_mode_deferral.py`** (новый файл)
Тесты на `count_deferred_by_mode` (прямая проверка очереди) и сквозной
прогон `Downloader.run()` в режиме 1 с CSS+картинкой на mock-странице.

**`docs/ROADMAP.md`**
Обновлён план: диагноз CSS-проблемы задокументирован в Этапе 2, пункты
фикса отмечены выполненными; известный баг с пагинацией (`scanner.py`,
`_scan_section`, ранее найденный и уже исправленный отдельно) зафиксирован
в Этапе 1.

# Патч №2 — пагинация раздела/темы и длина пути Windows (уже применён)

## Короткий вариант (однострочный commit message)

```
Fix section/topic pagination confusion in phpBB parser; fix Windows MAX_PATH crash on deep archive paths
```

---

## Развёрнутый вариант

### Что было исправлено

Два независимых бага, оба найдены при реальном прогоне архивации
форума №1 (phpBB).

**1. Путаница раздела и темы в пагинации.** `discover_pagination_urls`
искал ссылки с тем же `f=N` (id раздела) для подсчёта страниц пагинации
СПИСКА ТЕМ раздела, но не отличал такие ссылки от ссылки на конкретную
ТЕМУ этого же раздела с её последней прочитанной страницей
(`viewtopic.php?f=9&t=90&start=20` — тот же `f=`, тот же `start=`, но
это не то же самое, что `viewforum.php?f=9&start=20`). Значения `start=`
из ссылок на темы ошибочно попадали в число «страниц раздела» — сканер
листал десятки несуществующих страниц одного и того же раздела
вхолостую.

**2. Превышение лимита длины пути Windows (MAX_PATH, ~260 символов).**
`FileNotFoundError` при сохранении страниц с глубокой вложенностью
(`forum/sections/<раздел>/<подраздел>/topics/<тема>/page_001.html.tmp`).
Каждое отдельное имя папки ограничено 80 символами
(`safe_folder_name`), но суммарная длина всего пути (диск + папка
архива + `metadata/raw_html` + раздел + подраздел + `topics` + тема +
имя файла) легко превышает лимит при трёх уровнях вложенности.

### Изменения по файлам

**`parsers/phpbb_parser.py`**
`discover_pagination_urls` теперь дополнительно сверяет имя скрипта в
пути (`viewforum.php` vs `viewtopic.php`), не только параметр `f=`, —
отсекает ссылки на темы при подсчёте страниц раздела. Работает
одинаково корректно и для пагинации самих тем (`find_next_page_url`
использует ту же функцию с `current_url` вида `viewtopic.php?...`).

**`scanner/downloader.py`**
Новая функция `_long_path()`: на Windows абсолютный путь получает
префикс `\\?\`, снимающий ограничение MAX_PATH у Win32 API (до ~32000
символов). Применяется в `save_html_atomic`/`save_bytes_atomic`. На
других ОС не действует.

**`tests/test_phpbb_parser.py`, `tests/test_scanner.py`**
Прогнаны после фикса пагинации — регрессий нет.

**`tests/test_long_paths.py`** (новый файл)
Путь длиной 400+ символов сохраняется корректно (HTML и бинарный файл),
обычные короткие пути продолжают работать без изменений в поведении.

**`docs/ROADMAP.md`**
Оба бага задокументированы с диагнозом и статусом фикса; также
зафиксирована отдельная задача на будущее — очистить ~130 старых
дублей-«страниц» разделов, созданных ДО фикса пагинации (уже скачаны,
не блокируют работу, но занимают место).

# Патч №3 — разделы верхнего уровня никогда не переоткрывались (уже применён)

## Короткий вариант (однострочный commit message)

```
Fix Scanner never re-checking forum homepage for new top-level sections after first run
```

---

## Развёрнутый вариант

### Что было исправлено

Самый серьёзный из найденных багов. После полного цикла сканирование →
скачивание → переписывание в архиве форума №1 оказалась лишь малая
часть форума (4 раздела, 3 темы — при форуме на ~59 000 сообщений).

Причина: `scanner/scanner.py`, `_bootstrap_root_sections` — главная
страница форума (со списком разделов верхнего уровня) запрашивалась
ТОЛЬКО при самом первом запуске, когда таблица `sections` была ещё
пустой (`if any_sections: return True`). Если тот первый прогон
(скорее всего, тестовый режим с лимитом `test_mode.max_sections`) нашёл
лишь часть разделов, все последующие безлимитные запуски НИКОГДА
больше не переоткрывали главную страницу — новые разделы верхнего
уровня не находились, сколько раз ни перезапускай программу.

### Изменения по файлам

**`scanner/scanner.py`**
`_bootstrap_root_sections` теперь запрашивает главную страницу форума
при КАЖДОМ запуске `Scanner.run()`, а не только при первом. Уже
известные разделы не трогаются — `_insert_section` использует `INSERT
OR IGNORE`, их `scanned`-статус не сбрасывается; добавляются только
реально новые разделы (проверяется через `_section_exists` до вставки).
Побочный эффект (осознанный): каждый запуск теперь делает один
дополнительный сетевой запрос к главной странице, даже если всё уже
отсканировано — цена за корректность.

**`tests/test_scanner.py`**
Проверка resumability переписана: раньше тест проверял, что повторный
запуск НЕ делает сетевых запросов, если всё уже отсканировано — это и
была причина бага (тест закреплял неправильное поведение). Теперь
проверяет, что повторный запуск делает РОВНО один запрос (к главной
странице) и не сбрасывает `scanned` у уже известных разделов.

**`docs/ROADMAP.md`**
Баг задокументирован с диагнозом и статусом фикса; отмечена
необходимость перезапустить боевую архивацию форума №1 после переноса —
должны найтись дополнительные разделы верхнего уровня.

# Патч №4 — выборочная архивация по разделам (уже  применён)

## Короткий вариант (однострочный commit message)

```
Add optional section-level selective download (choose which sections to fetch instead of all-or-nothing)
```

---

## Развёрнутый вариант

### Зачем

Форум большой (~59 000 сообщений), сервер нестабильный, throttle
намеренно медленный (20-40 сек/запрос, надёжность важнее скорости) —
полный архив может не успеть скачаться. Нужна возможность заранее
выбрать самые важные разделы и качать в первую очередь их, не теряя
остальное. Реализовано как ДОПОЛНИТЕЛЬНЫЙ режим — «скачать всё» (по
умолчанию, пустой ввод) остаётся без изменений.

### Изменения по файлам

**`storage/database.py`**
- Новая колонка `tasks.section_id` (миграция, тем же способом, что
  `host` ранее) — заполняется только у `section_page`/`topic_page`.
- `QueueManager.add_task()` принимает опциональный `section_id`.
- `get_next_task()` и `host_backoff_wait_seconds()` принимают
  опциональный `allowed_section_ids: list[str]`. Без него (None)
  поведение не меняется — без ограничений, как раньше. С фильтром:
  `section_page`/`topic_page` берутся только если их `section_id` в
  списке; ресурсы (картинки/CSS/аватары/...) не имеют своего
  `section_id` — фильтруются через `section_id` родительской задачи
  (`parent_id`). Задачи невыбранных разделов остаются `pending`
  нетронутыми — ничего не удаляется и не помечается failed/skipped.

**`scanner/scanner.py`**
`_scan_section` передаёт `section_id` при постановке
`section_page`/`topic_page` в очередь. Сам Scanner не меняет
поведение — по-прежнему находит и ставит в очередь всё найденное;
ограничение применяется только на этапе скачивания.

**`scanner/downloader.py`**
`_discover_next_topic_page` (страница 2, 3... уже известной темы) тоже
передаёт `section_id` из `topics.section_id`. `Downloader.run()`
принимает опциональный `allowed_section_ids`, прокидывает его в оба
вызова `QueueManager`.

**`run_commands/run_archive.py`, `run_commands/run_forum2x2_archive.py`**
Новая функция `choose_sections_to_download()`: после сканирования,
перед скачиванием текста — показывает пронумерованный список ВСЕХ
известных разделов (из текущего и прошлых прогонов) с числом уже
найденных тем; ввод номеров через запятую (например `1,3,5`) или пусто
= скачать всё (поведение без изменений). Выбор передаётся и в
скачивание текста, и в скачивание ресурсов.

**`tests/test_selective_download.py`** (новый файл)
Два раздела на mock-сервере: фильтр по одному разделу скачивает только
его текст и его ресурсы; второй раздел остаётся нетронутым
(`status=pending`); последующий отдельный прогон с другим фильтром
докачивает второй раздел, не трогая уже готовый первый.

**`docs/ROADMAP.md`**
Фича задокументирована как реализованная; отмечено, что не реализовано
сознательно (отбор на уровне отдельных тем внутри раздела, сортировка
по активности) — гранулярность выбора сейчас на уровне целого
раздела/подфорума.
