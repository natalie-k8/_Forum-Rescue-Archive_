# Roadmap Forum Rescue Archive

Что планируется дальше, в порядке, в котором договорились двигаться.
Прошлое — в `CHANGELOG.md`, текущее устройство проекта — в
`ARCHITECTURE.md`. Этот файл — только про будущее.

Проект стал шире, чем «парсер, который скачивает страницы»: цель —
**надёжный автономный архиватор форумов**, сохраняющий не только
сообщения, но и структуру, ресурсы и (в перспективе) представляющий
архив в удобном виде. CHM, PySide6 и сборка `.exe` сознательно не
входят в ближайшие задачи — сначала нужен надёжный архив.

Если багфикс по ходу дела всё же не устроит и понадобится переписать
проект с нуля по тем же принципам — для этого уже подготовлена папка
`project_renew` рядом со старым кодом, который она не трогает.

- [x] Тесты `test_phpbb_parser.py` и `test_scanner.py` прогнаны после

- [x] **`scanner/scanner.py`, `_bootstrap_root_sections`.** Главная
      страница форума (со списком разделов верхнего уровня) запрашивалась

      часть разделов (например, из-за лимита `test_mode.max_sections`),
      все последующие безлимитные запуски НИКОГДА не переоткрывали
      главную страницу — новые разделы верхнего уровня не находились,

- [ ] **Перезапустить сканирование форума №1 после этого фикса** —

      следующем запуске должны обнаружиться остальные разделы верхнего
      уровня, если они есть на форуме.

### Превышение лимита длины пути Windows (MAX_PATH)

Найдено при реальном прогоне форума №1:

```
FileNotFoundError: [Errno 2] No such file or directory:
'Archive_phpbb_.../metadata/raw_html/forum/sections/.../topics/.../page_001.html.tmp'
```

- [x] **`scanner/downloader.py`, `save_html_atomic`/`save_bytes_atomic`.**

      символами (`safe_folder_name` в `storage/archive_paths.py`), но

      получает префикс `\\?\`, снимающий это ограничение у Win32 API
      (до ~32000 символов); на других ОС не действует.
- [x] Новый тест `tests/test_long_paths.py` — путь длиной 400+ символов
      сохраняется корректно (HTML и бинарный файл), обычные короткие
      пути продолжают работать без изменений в поведении.

## Этап 2. Отдельно решить проблему с внешним видом

Самая важная техническая задача после сохранения данных. Не значит
переписывать весь парсер — сначала диагностика на одной небольшой теме.

### Диагноз CSS уже найден — не регрессия, а поведение режима 1

Разбор на присланных HTML-страницах (обе темы, оба форума) показал:
**это не баг и не потеря функциональности**, а следствие того, в каком
режиме шёл прогон.

- `utils/config.py` (`ModeConfig`) — режим 1 «Спасение текста» имеет
  `priority_ceiling() == 1`, режим 2 «Полный архив» — `== 2`.
- `storage/database.py` — все текстовые задачи (страницы разделов/тем)
  имеют `priority = 1` (`PRIORITY_TEXT`); **все** ресурсы — картинки,
  вложения, аватары, смайлики и CSS — имеют `priority = 2`
  (`PRIORITY_RESOURCE`), без исключения для CSS.
- `Downloader.run()` берёт из очереди только задачи с
  `priority <= priority_ceiling` — в режиме 1 задачи на CSS **создаются**
  (`parsers/phpbb_parser.py`, `extract_resource_links`, корректно находит
  `<link rel="stylesheet">`), но никогда не скачиваются, пока режим не
  переключат на 2.
- `scanner/rewrite_html.py` при этом не ошибается и не падает — просто
  не находит CSS в `resource_map` (там только `status='done'`), поэтому
  ссылка на стиль остаётся непереписанной. В присланных файлах путь
  `./styles/prosilver/theme/stylesheet.css?...` — это исходный
  относительный путь самого сайта phpBB, а не переписанный локальный
  путь архива.

Вывод: раньше forum2x2 скачивался с оформлением, скорее всего, потому
что тот прогон шёл в режиме 2 — не потому что что-то с тех пор
сломалось. Задачи на CSS для уже скачанных архивов уже стоят в очереди
как `pending` — при переключении на режим 2 и повторном запуске текст
пересканировать не придётся, доскачаются только недостающие ресурсы.

- [x] `storage/database.py` — `QueueManager.count_deferred_by_mode()`:

- [x] `scanner/downloader.py` — новое поле `DownloadStats.resources_deferred_by_mode`,

- [x] `run_commands/run_archive.py` и `run_forum2x2_archive.py` (вывод

      режиме 1, явно печатается, сколько ресурсов (CSS/картинки/
      вложения/аватары) не скачано из-за режима «Спасение текста», и

## Этап 3. Сделать автоматическую проверку архива

### Видимость уже накопленного прогресса при запуске

Найдено при реальном прогоне форума №1: программа не начинает заново,
если архив уже существует (SQLite-очередь помнит, что уже `done`, и не
перескачивает это) — но при каждом запуске `run_archive.py`/
`run_forum2x2_archive.py` заново задаёт весь тот же вопросник (адрес,
режим, лимиты) и заново печатает `--- Сканирование структуры ---`,
из-за чего выглядит так, будто всё начинается с нуля, хотя по факту
это не так.

- [ ] Перед вопросником (или сразу после выбора/подтверждения архива)
      печатать сводку уже накопленного состояния: сколько разделов/тем
      уже известно, сколько текстовых страниц и сколько ресурсов уже
      `done` против `pending`, — чтобы пользователь сразу видел, что
      продолжается, а не начинается заново.
- [ ] **Отдельно найдено — молчание консоли похоже на зависание.**
      При реальном прогоне (форум №1, безлимитный режим) после выхода
      из backoff программа продолжала успешно скачивать десятки страниц
      подряд (проверено по БД: `consecutive_successes` дошло до 53,
      `section_page done` выросло с 25 до 79), но в консоли не появилось
      ни строки — `_process_text_task`/`_process_resource_task` в
      `scanner/downloader.py` логируют только предупреждения/ошибки, не
      обычный успех. Выглядело так, будто процесс завис на последней
      напечатанной строке ожидания backoff, хотя работа шла. Нужен
      периодический прогресс-лог (например, раз в N обработанных задач
      или раз в T секунд: «скачано X страниц, Y ресурсов, очередь: N
      pending») — чтобы отличать реальное зависание от молчаливой
      работы. Актуально уже для консоли, не только для будущего GUI.
      **Частично закрыто 2026-08-30:** один конкретный немой путь —
      ожидание backoff по ОТДЕЛЬНОМУ хосту (форум работает нормально,
      просто нет свободных задач с других хостов) — теперь логирует
      каждые 30 секунд. Общий периодический прогресс-лог по успешным
      задачам (пункт выше) всё ещё не реализован.

## Выборочная архивация по разделам

Реализовано по срочному запросу пользователя: форум большой (~59 000
сообщений), сервер нестабильный, времени может не хватить на полный
архив целиком — нужна возможность заранее выбрать самые важные разделы
и качать в первую очередь только их, не теряя остальное.

- [x] **`storage/database.py`** — новая колонка `tasks.section_id`
      (миграция, как `host` ранее). `QueueManager.add_task()` принимает
      опциональный `section_id`. `get_next_task()` и
      `host_backoff_wait_seconds()` принимают опциональный
      `allowed_section_ids: list[str]` — без него (None) поведение как
      раньше, без ограничений. С фильтром: `section_page`/`topic_page`
      берутся только если их `section_id` в списке; ресурсы
      (картинки/CSS/аватары/...) не имеют своего `section_id` — для них
      проверяется `section_id` родительской задачи через `parent_id`.
      Задачи невыбранных разделов остаются в очереди `pending`
      нетронутыми — ничего не удаляется и не помечается
      failed/skipped, доступны для скачивания в следующий раз.
- [x] **`scanner/scanner.py`** — `_scan_section` передаёт `section_id`
      при постановке `section_page`/`topic_page` в очередь. Сам Scanner
      не меняет поведение — находит и ставит в очередь всё, как раньше;
      ограничение применяется только на этапе скачивания.
- [x] **`scanner/downloader.py`** — `_discover_next_topic_page` (страница
      2, 3... уже известной темы) тоже передаёт `section_id` из
      `topics.section_id`. `Downloader.run()` принимает опциональный
      `allowed_section_ids`, прокидывает его в оба вызова `QueueManager`.
- [x] **`run_commands/run_archive.py`, `run_forum2x2_archive.py`** —
      новая функция `choose_sections_to_download()`: после сканирования,
      перед скачиванием текста — показывает пронумерованный список ВСЕХ
      известных разделов (из текущего и прошлых прогонов) с числом уже
      найденных тем, даёт ввести номера через запятую (например `1,3,5`)
      или оставить пустым для "скачать всё" (поведение без изменений).
      Выбор передаётся и в скачивание текста, и в скачивание ресурсов.
- [x] Новый тест `tests/test_selective_download.py` — два раздела на
      mock-сервере, проверено: фильтр по одному разделу скачивает только
      его текст и его ресурсы, второй раздел остаётся нетронутым
      (`status=pending`), последующий отдельный прогон с другим фильтром
      docкачивает второй раздел, не трогая уже готовый первый. Вся сюита
      (12 файлов) прогнана — регрессий нет.

**Не реализовано (сознательно, чтобы не усложнять первую версию):**
отбор на уровне отдельных ТЕМ внутри раздела (сейчас гранулярность —
только целый раздел/подфорум); критерии "важности" вроде сортировки по
активности/числу ответов — пользователь выбирает разделы вручную по
названию.

## Реализовано 2026-08-30 (было открытым вопросом)
