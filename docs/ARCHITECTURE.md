# Архитектура Forum Rescue Archive

Этот файл описывает, как проект устроен **прямо сейчас**. Обновляется
после каждого завершённого этапа доработки — актуальную картину нужно
искать здесь, а не в истории переписки.

## Текущая структура каталогов

```
Forum Rescue Archive/
├── main.py                  ← точка входа: текстовое меню команд
├── run_commands/            ← скрипты-команды, которые вызывает main.py
│   ├── run_archive.py               (боевая архивация форума №1)
│   ├── run_forum2x2_archive.py      (боевая архивация форума №2)
│   ├── run_scan_test.py             (тестовый скан форума №1)
│   ├── run_download_test.py         (тестовое скачивание форума №1)
│   ├── run_forum2x2_download_test.py (тестовое скачивание forum2x2)
│   ├── run_forum2x2_smoketest.py    (проверка парсера на одной странице)
│   └── debug_login.py               (диагностика входа на форум №1)
├── parsers/                 ← разбор HTML конкретного движка форума
│   ├── phpbb_parser.py
│   └── forum2x2_parser.py
├── network/
│   └── http_client.py       ← ForumClient: запросы, вход, повтор при сбоях
├── storage/
│   ├── database.py          ← SQLite-очередь заданий (QueueManager);
│   │                            задачи хранят раздел (section_id) —
│   │                            для выборочной архивации и режима
│   │                            (priority_ceiling) — для CSS/ресурсов
│   └── archive_paths.py     ← пути к файлам внутри архива
├── scanner/
│   ├── scanner.py           ← обход структуры форума; главная страница
│   │                            перепроверяется на новые разделы при
│   │                            КАЖДОМ запуске, не только при первом
│   ├── downloader.py        ← скачивание текста и ресурсов; умеет
│   │                            ограничиваться выбранными разделами
│   │                            (allowed_section_ids)
│   └── rewrite_html.py      ← переписывание ссылок на локальные пути
├── utils/
│   ├── config.py            ← настройки (AppConfig, config.json)
│   ├── credentials.py       ← чтение логина/пароля из .env
│   ├── logger_setup.py      ← настройка логов
│   └── site_registry.py     ← реестр форумов на общем хостинге (forum2x2):
│                                своя папка архива и свой config на каждый
│                                новый адрес, без ручного именования
├── tests/                   ← тестовые файлы (обычные скрипты с
│                                mock-сервером внутри, без фреймворка)
└── docs/
    ├── ARCHITECTURE.md      ← этот файл
    └── CHANGELOG.md
```

**Важно: этот слой (`parsers`/`network`/`storage`/`scanner`/`utils`) в
будущем станет пакетом `core/`** — см. раздел «Куда движется архитектура»
ниже. Перенос ещё не выполнен, структура выше — что есть на диске сейчас.

## Как данные текут через систему

```
run_commands/*.py  (или main.py → run_commands/*.py)
        │
        ├─ читает настройки            → utils/config.py
        ├─ читает логин/пароль          → utils/credentials.py
        │
        ▼
scanner/scanner.py  (обход структуры)
        │
        ├─ HTTP-запросы, вход           → network/http_client.py
        ├─ разбор HTML                  → parsers/phpbb_parser.py ИЛИ
        │                                  parsers/forum2x2_parser.py
        │                                  (какой именно — параметр parser=)
        ├─ пути внутри архива           → storage/archive_paths.py
        └─ очередь задач, прогресс      → storage/database.py (SQLite)
        │
        ▼
scanner/downloader.py  (скачивание текста и ресурсов)
        │  (те же зависимости, что у Scanner)
        ▼
scanner/rewrite_html.py  (переписывание ссылок на локальные пути)
```

`Scanner` и `Downloader` не привязаны жёстко к одному движку форума — они
принимают параметр `parser` (модуль `parsers/phpbb_parser` или
`parsers/forum2x2_parser`), плюс каждый парсер может объявить две
дополнительные точки расширения:

- `HOME_PAGE_PATH` — путь к главной странице форума (у phpBB это
  `index.php`, у forum2x2 — пустая строка, сам `base_url`);
- `LOGIN_METHOD_NAME` — какой метод `ForumClient` вызывать для
  (повторного) входа (`login` для phpBB, `login_forum2x2` для forum2x2).

Так основной код скачивания один на оба форума — добавление третьего
движка потребует только нового файла в `parsers/` и, при необходимости,
нового метода входа в `network/http_client.py`.

## Устойчивость к сбоям (backoff)

`storage/database.py` (`QueueManager`) различает два уровня backoff:

- **Глобальный** — если ошибается сам форум (`host == own_host`), это
  считается сбоем всего сервера, и новые запросы приостанавливаются.
- **По отдельному хосту** — если ошибается сторонний хост (например,
  мёртвая ссылка на устаревший фотохостинг), в backoff уходит **только
  этот хост** — скачивание всего остального, включая сам форум,
  продолжается. Активируется передачей `own_host=<хост форума>` при
  создании `QueueManager` — это уже сделано во всех скриптах
  `run_commands/`.

## Выборочная архивация по разделам

`tasks` хранит `section_id` — раздел, к которому принадлежит
`section_page`/`topic_page` (заполняет `Scanner` при постановке в
очередь; ресурсы вроде картинок/CSS своего `section_id` не имеют — их
раздел определяется через `parent_id`, ссылающийся на родительскую
текстовую задачу).

`QueueManager.get_next_task()` и `host_backoff_wait_seconds()`
принимают опциональный `allowed_section_ids: list[str]`. Без него (по
умолчанию, `None`) поведение как раньше — выдаётся всё доступное. Если
задан список — выдаются только задачи выбранных разделов (плюс их
ресурсы), задачи остальных разделов остаются `pending` нетронутыми,
доступными для докачки в другой раз.

`run_commands/run_archive.py` и `run_forum2x2_archive.py` после
`Scanner.run()` и перед `Downloader.run()` вызывают
`choose_sections_to_download()` — показывают пронумерованный список
всех известных на данный момент разделов (из текущего и прошлых
прогонов сканирования) с числом уже найденных тем; пустой ввод =
скачать всё. Выбранный список `section_id` передаётся в оба вызова
`Downloader.run()` (текст и ресурсы) через параметр
`allowed_section_ids`.

Причина появления: форум может быть большим (десятки тысяч сообщений),
а время или доступность сервера — ограничены; это даёт возможность
сперва гарантированно сохранить самое важное, не дожидаясь архива
целиком.

## Куда движется архитектура (согласовано, ещё не выполнено)

Следующий этап — обернуть текущий код бизнес-логики в единый пакет
`core/`, добавить между GUI и core тонкий слой `controller/`, и уже
поверх него в будущем можно будет заменить Streamlit-интерфейс (этап 6)
на полноценное Windows-приложение (PySide6), не переписывая ядро:

```
GUI (Streamlit → в будущем PySide6)
        ↓
Controller  (новый слой, тонкий, без бизнес-логики)
        ↓
Core        (parsers/network/storage/scanner — сегодняшний код,
              перенесённый под core/ почти без изменений)
        ↓
SQLite
```

`run_commands/` при этом продолжит обращаться к `core/` напрямую, в обход
`Controller` — переводить консольные команды на `Controller` не
планируется, раз они уже работают и протестированы. `Controller` — это
новый, отдельный вход, специально под GUI.
